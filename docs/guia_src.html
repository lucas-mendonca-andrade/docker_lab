docker_lab

Guia de instalação e uso — execução de experimentos com CPU, RAM e GPU controlados em servidor compartilhado
Projeto: github.com/lucas-mendonca-andrade/docker_lab

1. Para que serve

Vários alunos usam a mesma máquina de laboratório. Sem controle, um único experimento pesado podia esgotar CPU, memória ou GPU, derrubar o acesso remoto de todos e até reiniciar a máquina. O docker_lab resolve isso com três mecanismos:

Execução em containerTodo script Python roda dentro de um container Docker, com a quantidade de CPU, RAM e VRAM que o próprio aluno pediu, e nada além disso.
Teto de 80% da máquinaA soma do que todos os jobs reservaram nunca passa de 80% de cada recurso. Um pedido que ultrapassaria o teto é recusado na hora.
Proteções na máquinaA potência da GPU fica limitada a 80%, e rodar python3 direto no terminal mostra um aviso em vez de executar.

Como uma execução acontece

O processamento da GPU não é reservado por job: quando dois jobs usam a mesma GPU, o driver da NVIDIA alterna entre eles, e cada um fica proporcionalmente mais lento.

2. Instalação (administrador, uma única vez)

A instalação é feita na máquina do laboratório por quem tem sudo. São dois comandos:

sudo git clone https://github.com/lucas-mendonca-andrade/docker_lab.git /opt/docker_lab
sudo /opt/docker_lab/setup.sh
Instale em /opt/docker_lab, como root, e não mova a pasta depois. Se a pasta ficar na home de um aluno, os outros usuários não conseguem acessá-la, e esse aluno poderia alterar scripts que rodam como root. Para mudar de lugar: undo.sh, mover a pasta e rodar setup.sh de novo.

O setup.sh faz quatro coisas, e pode ser rodado de novo sem problema (por exemplo, depois de um git pull):

PassoO que faz
1. Instalação compartilhadaLibera state/ e logs/ para todos os usuários, que passam a gravar no mesmo controle de reservas. Usuários criados no futuro já funcionam, sem nenhum comando extra.
2. Potência da GPULimita cada GPU a 80% da potência de fábrica e instala um serviço do systemd que reaplica o limite a cada boot.
3. Comando docker-labInstala o comando docker-lab para todos os usuários.
4. Bloqueio de Python diretoFaz python3 script.py no terminal mostrar um aviso em vez de executar, inclusive com venv ativado. Os binários do sistema não são alterados.
Quem estava conectado por SSH durante a instalação só passa a ter o bloqueio completo de Python depois de reconectar. Para desfazer tudo: sudo /opt/docker_lab/undo.sh. Ele remove o bloqueio, volta a GPU à potência de fábrica, remove o comando docker-lab e devolve as permissões originais. Histórico e logs são preservados.

3. Executando um experimento (cada aluno)

Passo 1 — Criar o job.env na raiz do projeto

cp /opt/docker_lab/job.env.example ~/meu_projeto/job.env

O job.env fica sempre na raiz do projeto. A pasta onde ele está é montada dentro do container, e os caminhos SCRIPT e PYTHON_BIN são relativos a ela.

VariávelExemploSignificado
SCRIPTtreino.pyScript a executar, relativo à raiz do projeto
PYTHON_BINvenv/bin/pythonPython usado. Normalmente é o venv do próprio projeto; são aceitos venvs de Python 3.9 a 3.12.
CORES2Quantidade de cores. O docker_lab escolhe quais cores livres usar.
MEMORY_GB4RAM máxima do job
GPUnone ou 0Não usar GPU (none) ou usar a GPU de índice 0, a primeira coluna do nvidia-smi
GPU_MEMORY_GB2VRAM máxima (obrigatório com GPU)
JOB_NAME{USERNAME}_treinoNome do job. Mantenha o {USERNAME}_, que é trocado pelo seu usuário automaticamente.
O nvidia-smi mostra cerca de 0,3 GB a mais que o GPU_MEMORY_GB por job: é a memória fixa que o driver reserva para cada processo (contexto CUDA), e o teto de 80% já deixa folga para ela. Não sabe quanta VRAM o seu script usa? Rode uma vez e veja o pico: torch.cuda.max_memory_allocated() no PyTorch, ou nvidia-smi durante a execução.

Passo 2 — Executar com docker-lab run

Abra o terminal do VS Code na pasta do projeto e rode docker-lab run. A validação e a reserva aparecem na tela, o job segue em segundo plano e o prompt volta na hora. Você pode fechar o VS Code ou desconectar, e o job continua rodando.

Passo 3 — Acompanhar: docker-lab status e o log

docker-lab status mostra o que cada recurso tem em uso, o que ainda pode ser reservado dentro do teto de 80% e quais jobs estão ativos. O andamento do script fica no log.

O job roda com o seu usuário: tudo o que o script gravar no projeto (resultados, modelos, logs) é seu, e você pode apagar ou editar sem sudo. Só instalar e desinstalar o docker_lab exige sudo.

Passo 4 — Parar um job e ver o histórico

docker-lab stop lista os jobs ativos num menu numerado. Parar um job encerra a execução, que não pode ser retomada depois. A reserva é liberada sozinha. docker-lab history mostra todas as execuções com início, fim e status: executando, executou, erro ou interrompido.

4. O que o docker_lab impede

Rodar Python direto, fora do container

Com o bloqueio ativo, python3 script.py no terminal mostra instruções em vez de executar, inclusive com o venv ativado. A sessão do terminal continua normal.

O bloqueio é uma barreira contra esquecimento, não uma trava de segurança. Caminhos absolutos (/usr/bin/python3.11 x.py), ./script.py e scripts .sh não interativos passam sem aviso. Use sempre o docker-lab run.

Passar do teto de 80%

Se o pedido de um job, somado ao que já está reservado, passar do teto de qualquer recurso, a execução é recusada na hora, com a explicação do motivo. Nada entra em fila: espere algum job terminar, ou peça menos recurso.

Passar do limite do próprio job

SituaçãoO que aconteceO que fazer
O script usa mais RAM que MEMORY_GBO container é encerrado. O histórico mostra erro.Aumentar MEMORY_GB
O script usa mais VRAM que GPU_MEMORY_GBO script recebe CUDA out of memory, e só esse job é afetado.Aumentar GPU_MEMORY_GB ou reduzir o batch size
O script pede mais cores (ex. n_jobs=-1)Ele só enxerga os cores reservados e roda com eles.Nada: é o esperado

sudo /opt/docker_lab/undo.sh
